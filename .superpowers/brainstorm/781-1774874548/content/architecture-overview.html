Arquitectura recomendada

SaaS multi-tenant compartido por defecto, con customización controlada y aislamiento premium sólo cuando tenga sentido comercial.

1. Vista lógica del sistema
Entrada

Usuarios

Recepción, odontólogos, admins y dueños de clínica.

→
UI

Frontend web

Una sola app para todos los tenants, con branding y módulos activables por plan o cliente.

→
Core

Backend modular

Auth, agenda, pacientes, historia clínica, tratamientos, caja, reportes e integraciones.

Datos

PostgreSQL compartido

Separación por tenant_id y camino abierto a DB dedicada para premium.

Async

Worker / Jobs

Recordatorios, PDFs, tareas asíncronas e integraciones con terceros.

Archivos

Object storage

Imágenes, PDFs y adjuntos clínicos separados por tenant.

2. Camino de tenancy
Estándar

Shared app + Shared DB

Es la opción base para la mayoría: menor costo, menor fricción y releases más simples.

Custom

Shared app + módulos exclusivos

Se habilitan features o integraciones específicas por tenant sin duplicar toda la plataforma.

Premium

Dedicated DB o Dedicated Stack

Sólo cuando hay una razón comercial fuerte, compliance o necesidad técnica real.

3. Regla para customizaciones
Orden recomendado:
configuración → flags → módulo opcional → integración por tenant → workflow específico → DB dedicada → stack dedicado.

Evitar: forks por cliente y if cliente_x desparramados por todo el core.
